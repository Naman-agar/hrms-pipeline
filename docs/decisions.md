# Decisions made where a TPRD was silent

(one line per decision: TPRD, section, choice)

- TPRD 01 §1: lint config is `@typescript-eslint/recommended` + `plugin:prettier/recommended` with no custom rules; Prettier uses singleQuote, trailingComma=all, printWidth=100 (not specified).
- TPRD 01 §2: added `tsconfig.build.json` (src only) alongside `tsconfig.json` (src+test+prisma) so `nest build` excludes tests/seed while `tsc --noEmit` checks everything (not specified).
- TPRD 01 §3: `npm test` maps `DATABASE_URL_TEST` onto `DATABASE_URL` in `vitest.config.ts`, defaulting to `postgresql://hrms:hrms@localhost:5432/hrms_test`; `.env.example` keeps only the §3 variables with `DATABASE_URL_TEST` as a comment (not specified).
- TPRD 01 §1: Vitest uses `unplugin-swc` so decorator metadata is emitted for Nest DI; e2e files run sequentially (`fileParallelism: false`) against the single test DB, with `test/setup.ts` as the setup file (not specified).
- TPRD 01 §2: docker-compose services are `postgres` (user/password/db `hrms`) and `redis`, matching `.env.example`; both have healthchecks, postgres data in a named volume (not specified).
- TPRD 01 §4: migrations hand-written as `20261028000000_init` and `20261028000001_trgm_indexes` (no node_modules to run `prisma migrate dev`); relations use Prisma defaults `ON DELETE RESTRICT ON UPDATE CASCADE`, `invitedById` is a plain column with no relation (not specified).
- TPRD 01 §3: all 12 env vars are required with no defaults; `DATABASE_URL`/`REDIS_URL`/`FRONTEND_URL` must parse as URLs, `MAIL_FROM` as an email, `PORT`/`INVITE_TTL_HOURS` as positive integers, TTLs and `CORS_ORIGINS` stay raw strings for 02-auth / `main.ts` to interpret; invalid env throws `ConfigError` listing every offending variable (not specified).
- TPRD 01 §3: `config.ts` does `import 'dotenv/config'` and exposes the parsed object through a `CONFIG` symbol token from a `@Global() ConfigModule` (`@Inject(CONFIG) config: Config`), with `parseConfig(env)` pure and `loadConfig()` memoised for the process (not specified).
- TPRD 01 §6.1: `VALIDATION_ERROR` responses use the fixed message `Validation failed`; `fields` keys are `issue.path.join('.')`, an empty path is keyed `_root`, and the first issue per path wins (not specified).
- TPRD 01 §6.1: Nest's own `HttpException`s (404 on an unknown route, 403 from a guard, …) keep their own status; `code` is the class name minus `Exception` as UPPER_SNAKE (`NotFoundException` → `NOT_FOUND`; bare `HttpException` falls back to the `HttpStatus` enum name), `message` is the framework message, no `fields`/`details`; logged at warn (error for 5xx) without a stack (not specified).
- TPRD 01 §6.1: `HttpExceptionFilter` takes nestjs-pino's singleton `Logger` in its constructor so `main.ts` can register it with `app.useGlobalFilters(new HttpExceptionFilter(app.get(Logger)))`; `PinoLogger` is transient and would need `app.resolve`. 500s are logged at error level as `{ err, requestId: req.id, method, url, status }`; the client sees the fixed message `Internal server error` (not specified).
- TPRD 01 §6.2: `skip`/`take` are derived by a standalone `toSkipTake({ page, page_size })` helper exported from `pagination.dto.ts` rather than schema getters, keeping `PaginationSchema`'s inferred type a plain `{ page, page_size }`; `paginate()` is typed via exported `Paginated<T>` / `PaginationMeta` interfaces and `total_pages` floors at 1 for an empty result (not specified).
- TPRD 01 §2/§4: `PrismaService extends PrismaClient` takes `@Inject(CONFIG) config` and passes `datasources.db.url = config.DATABASE_URL` to `super()` so Prisma never reads `process.env` itself; `onModuleInit` calls `$connect()` eagerly (bad URL fails at boot) and `onModuleDestroy` calls `$disconnect()`; exposed via a `@Global() PrismaModule` that imports `ConfigModule` (not specified).
- TPRD 01 §7: `AuthGuard` stub attaches the loaded user (with `role` + `department`) to `request.user`; a missing/blank `x-user-id`, an unknown id, or a soft-deleted user all → 401 `UNAUTHENTICATED` (status `inactive`/`suspended` is not checked by the stub — 02-auth owns that); the request is typed structurally as `RequestWithUser { headers, user? }` rather than importing Express types (not specified).
- TPRD 01 §7: `PermissionsGuard` reads `@Permissions()` metadata via `reflector.getAllAndOverride` (handler first, then controller class); no metadata or an empty list → pass-through; metadata present but no `request.user` → 401 `UNAUTHENTICATED`; any required permission missing from `role.permissions` → 403 `FORBIDDEN` (not specified).
- TPRD 01 §5: `prisma/seed.ts` runs standalone with `import 'dotenv/config'` and a bare `new PrismaClient()` (Prisma resolves `DATABASE_URL` itself) since `ts-node prisma/seed.ts` runs outside Nest DI; all writes happen in one `$transaction` so a half-seeded DB is impossible, and the 72 h invitation window is a local constant mirroring `INVITE_TTL_HOURS=72` (not specified).
- TPRD 01 §5: Rahul's seeded `Invitation` uses `tokenHash = sha256(base64url(randomBytes(32)))` hex (the nest-prisma-patterns token convention, inlined with `node:crypto` because `src/common/crypto/tokens.ts` does not exist yet) and `invitedById = Asha`'s id; it is created only when Rahul has no `Invitation` row at all, so re-seeding never adds a second one (not specified).
- TPRD 01 §5: user upserts re-apply every §5 field on update and also reset `deletedAt = null`; role upserts re-apply `permissions`/`isSystem`; department upserts update nothing beyond matching on `name` (not specified).
- TPRD 01 §6.3: `AuditService.log(input, tx?)` takes an optional `Prisma.TransactionClient` and writes via `(tx ?? prisma).auditLog.create`, returning the created `AuditLog` row; it never opens its own transaction. `actorId` is typed `string | null` (column is nullable, for actor-less events such as failed logins), `action` stays a plain `string` so later TPRDs can add actions without touching this file, and an omitted `metadata` is stored as SQL `NULL` via `Prisma.JsonNull` (not specified).
- TPRD 01 §6.3: `AuditModule` only provides/exports `AuditService` and imports nothing — `PrismaService` is resolved from the `@Global() PrismaModule` (not specified).
- TPRD 01 §6.4: queue wiring uses the `@nestjs/bullmq` wrapper already in package.json — `BullModule.forRootAsync` lives inside `MailModule` (imports `ConfigModule`, injects `CONFIG`) with `connection: { url: config.REDIS_URL, maxRetriesPerRequest: null }`, plus `BullModule.registerQueue({ name: 'mail' })`; `MailModule` re-exports `BullModule` so importers/tests can `@InjectQueue('mail')` (not specified).
- TPRD 01 §6.4: the provider adapter is resolved once at boot behind a `MAIL_PROVIDER` symbol token (`src/mail/providers/mail-provider.interface.ts`); `console` → `ConsoleMailProvider`, `ses`/`sendgrid` → `UnsupportedMailProvider` whose `send()` throws a plain `Error` (not `AppError`) so the app still boots and the job fails through BullMQ's retry path (not specified).
- TPRD 01 §6.4: the job payload stays exactly `{ template, to, vars }`; the subject comes from a per-template map in `mail.processor.ts` (`invite` → "You have been invited to HRMS") and `from` is `config.MAIL_FROM`; `RenderedMail` handed to adapters is `{ to, from, subject, html }` (not specified).
- TPRD 01 §6.4: `ConsoleMailProvider` logs one structured entry `{ msg: 'mail.rendered', to, from, subject, html }` through Nest's `@nestjs/common` `Logger` (no `LoggerModule` dependency; routed to pino once `main.ts` calls `app.useLogger`) (not specified).
- TPRD 01 §6.4: `MailService.send()` uses the template name as the BullMQ job name and returns the created `Job` (callers may ignore it); `MailJob`/`MailTemplate`/`MailTemplateVars` are typed per template in `src/mail/mail.types.ts`; the processor caches compiled templates per worker and rejects unknown template names before touching the filesystem (not specified).
- TPRD 01 §6.4: `invite.hbs` renders `inviteUrl` with triple-stash (`{{{inviteUrl}}}`) because the URL is server-built and Handlebars' escaping would turn `=` into `&#x3D;`; `firstName`/`expiresInHours` stay HTML-escaped (not specified).
- TPRD 01 §2/AC-F2: health body is always `{ status, db, redis }` with `db`/`redis` ∈ `"ok" | "down"` and `status` = `"ok"` only when both are up, otherwise `"error"`; any `"down"` → HTTP 503 with the same body (not the error envelope), set via `@Res({ passthrough: true })` since the code depends on the result (not specified).
- TPRD 01 §2/AC-F2: `HealthService` probes DB with `prisma.$queryRaw\`SELECT 1\`` and Redis with a throw-away ioredis client (`lazyConnect`, no reconnects, no offline queue) that is `PING`ed and disconnected per call, so an outage never spams reconnect errors between checks; each probe is capped at `HEALTH_PROBE_TIMEOUT_MS = 2000` and a timeout/throw reports `"down"` rather than 500 (not specified).
- TPRD 01 §2/AC-F2: `GET /health` is unauthenticated and marked with a new `@Public()` decorator (`src/common/decorators/public.decorator.ts`, metadata key `IS_PUBLIC_KEY`); the globally registered auth guard (task 14 / 02-auth) must honour it (not specified).
- TPRD 01 §7 (roles): `PATCH /roles/{id}` body is `{name?, permissions?}` (both optional, same validation as POST: name trimmed, 1–100 chars; permissions an array of non-empty strings); an empty body is a no-op update (not specified).
- TPRD 01 §7 (roles): `POST /roles` (201) and `PATCH /roles/{id}` (200) respond with `{id,name,isSystem,permissions}` — permissions included because the caller must hold `roles.manage`; `GET /roles` stays `[{id,name,isSystem}]` as specified. `DELETE /roles/{id}` responds 204 with no body (not specified).
- TPRD 01 §7 (roles): an unknown `{id}` on PATCH/DELETE → 404 `NOT_FOUND`, the code TPRD 03 §4/§error-codes and 04 §3 use for missing role/department rows; `{id}` must be a uuid, otherwise 400 `VALIDATION_ERROR` (not specified).
- TPRD 01 §7 (roles): `NAME_TAKEN` is detected from Prisma `P2002` on the `Role.name` unique index (no pre-select), for both create and rename, with `fields.name = "already taken"`; on DELETE, `SYSTEM_ROLE` is checked before `IN_USE`, and `IN_USE` counts every user with the role including soft-deleted ones, since the FK still references it (not specified).
- TPRD 01 §7 (departments): an unknown `{id}` on `PATCH`/`DELETE /departments/{id}` → 404 `NOT_FOUND` (`AppError`), checked by loading the row before any other check; TPRD 01 names no not-found code for reference data (not specified).
- TPRD 01 §7 (departments): response DTO is `{ id, name, isActive }` (camelCase, mirroring the `[{id,name,isSystem}]` shape the table gives for roles and the `{name?, isActive?}` PATCH body); `createdAt`/`updatedAt` are not exposed (not specified).
- TPRD 01 §7 (departments): `POST` returns 201 with the created DTO, `PATCH` returns 200 with the updated DTO, `DELETE` returns 204 with no body; `NAME_TAKEN` carries `fields: { name }`, `IN_USE` carries `details: { users: <count> }` (not specified).
- TPRD 01 §7 (departments): request bodies are validated per-route with `@Body(new ZodValidationPipe(Schema))` from nestjs-zod so the module does not depend on `main.ts` registering a global pipe; `name` is trimmed and must be non-empty, no max length; `{id}` is taken as a plain string (a non-existent id simply 404s) (not specified).
- TPRD 01 §7 (departments): `NAME_TAKEN` is detected by catching Prisma `P2002` from the `Department.name @unique` constraint on both `POST` and `PATCH` (no pre-read, so a concurrent insert cannot slip past the check) (not specified).
- TPRD 01 §2/§6.5 (app.module): nestjs-pino is registered as `LoggerModule.forRoot({ pinoHttp: { redact: ['req.headers.authorization', 'req.headers.cookie'] } })` rather than `forRootAsync` injecting `CONFIG` — no §3 variable concerns logging, and an injected-but-unused factory argument fails `@typescript-eslint/no-unused-vars`; the DI result (`app.get(Logger)` in main.ts) is identical. Global guards are two `APP_GUARD` providers in `AppModule.providers`, `AuthGuard` before `PermissionsGuard`; `HttpExceptionFilter` is not an `APP_FILTER` (main.ts registers it via `useGlobalFilters`) (not specified).
- TPRD 01 §6.5 (main.ts): `bootstrap()` calls `loadConfig()` as step 1 and is wrapped in `.catch`; a `ConfigError` (from step 1 or from `ConfigModule`'s factory inside `NestFactory.create`) prints only `err.message` via `console.error` and exits 1, so AC-F1's "message naming the variable" is a clean one-liner rather than a Nest stack trace; any other boot failure (DB unreachable, port busy) is printed in full and also exits 1 (not specified).
- TPRD 01 §6.5 (main.ts): `NestFactory.create(AppModule, { bufferLogs: true })` followed immediately by `app.useLogger(app.get(Logger))` so Nest's own boot logs are routed through pino; one `logger.log` line is emitted after `listen` naming the port, prefix and docs path (not specified).
- TPRD 01 §6.5 (main.ts): the global pipe is nestjs-zod's `new ZodValidationPipe()` with no schema (only acts on `createZodDto` params); existing controllers keep their per-route `@Body(new ZodValidationPipe(Schema))`, so the global pipe is additive. `helmet()` runs with default options; `CORS_ORIGINS` is split on `,` with no trimming, exactly as the TPRD writes it (not specified).
- TPRD 01 §6.5 (main.ts): Swagger is `DocumentBuilder` title `HRMS API`, description `Backend for the HRMS User-management screen`, version `1.0`, mounted with `SwaggerModule.setup('api/docs', …)` at the default `useGlobalPrefix: false`, so it lives at `/api/docs` and not `/api/v1/api/docs` (not specified).
- TPRD 01 §7 (departments): `DELETE` also maps Prisma `P2003` (FK `User.departmentId` ON DELETE RESTRICT) to the same 409 `IN_USE` — reachable when a department's only users are soft-deleted, which the "any non-deleted user" pre-check intentionally ignores; without this the client would get 500 `INTERNAL` (reviewer finding, not specified).
